# 水色物语产品规格与 GitHub 实施路线

> 本文是产品与工程执行基线。当前只整理规划，不代表文档中列出的所有功能已经实现。
> 目标仓库：`water1014/water-`
> 工作分支：`feat/pure-frontend-polish`
> 禁止操作：修改 `main/master`、合并现有 PR、未经确认清空或覆盖用户数据、提交任何真实 API Key / Cookie。

## 1. 产品定位

水色物语是一间只属于用户与 AI 伴侣的私人生活空间，以手机为主要设备。它不是社交平台、公开角色广场或普通管理后台。核心价值是自然、持续、私密的陪伴，以及围绕共同生活沉淀的聊天、照片、日记、信件与记忆。

### 设计原则

- 手机优先，优先适配 Android 常见屏幕与 WebView。
- 保留水色物语现有开屏、晨雾蓝配色、精致细线图标与应用式首页。
- 首页横向分页的手势和吸附体验属于既有交互资产，除非发现明确 bug，不重写、不替换。
- 视觉以水蓝、雾蓝、灰蓝为主，采用轻磨砂或哑光质感；避免奶油色、紫色、棕色、过重透明玻璃、笨重卡片、杂乱与可爱风。
- 优先沿用当前原生 HTML/CSS/JavaScript 结构，不为“架构漂亮”而引入大型框架或构建系统。
- 用户数据优先保存在设备本地；任何迁移先备份、后验证、可回滚。

## 2. 当前基线

当前分支已经包含以下产品结构与能力（实施前仍需逐项回归验证）：

- 开屏 / 锁屏 / 主屏三屏横向滑动。
- 情侣屏、应用屏、氛围屏，以及 Dock 快捷入口。
- 聊天：模型 Endpoint、API Key、模型名、自定义请求头、流式回复等基础配置。
- 相册、手帐、信件、记忆库、星河/更多、音乐入口、设置。
- 主题切换、壁纸、纪念日、问候语、状态词等配置。
- 本地数据与 JSON 备份 / 导入。
- Service Worker 离线外壳缓存。
- 音乐入口目前曾采用“填写独立音乐服务 URL 并 iframe 打开”的过渡设计；这不等于原版音乐项目已部署，也不等于 Cookie 登录已经可用。

## 3. 信息架构

### 首页

1. **情侣屏**：头像、关系天数、时间/状态、心情记录。
2. **应用屏**：相册、手帐、信件、记忆库、星河、音乐、设置、更多。
3. **氛围屏**：今日低语、最近照片、近期记忆与共同生活摘要。
4. **Dock**：聊天、记忆库、音乐、设置快捷入口。

保持横向滑动、分页圆点与点击应用图标的原有交互。新增入口优先放入现有应用屏或 Dock，不另造复杂导航。

### 模块职责

| 模块 | 核心职责 | 当前状态 |
|---|---|---|

| 相册 | 照片保存、说明、查看与删除 | 已有基础，需验证图片持久化 |

## 4. 关键用户流程

### 首次打开

开屏 → 锁屏 → 解锁 → 主屏。首次使用提示 API 配置、纪念日与数据备份，不强迫用户注册账号或连接云端。

### 聊天

聊天入口 → 选择当前 API 配置 → 发送文本/图片 → 展示流式回复 → 本地保存消息。接口失败时保留用户输入并提供重试，不生成假回复，不丢失草稿。

### 记录生活

相册 / 手帐 / 信件 → 新建内容 → 本地保存 → 可在氛围屏显示最近内容。离线时仍可创建和编辑。

### 音乐

音乐入口 → 检查服务是否已连接 → 已连接时打开上游原版界面；未连接时显示明确说明与连接状态，不展示伪造的歌曲、播放进度或登录成功状态。

## 5. 数据与本地持久化

### 当前数据范围

需兼容现有键名，不能直接推翻现有存储：

- `mizu.config`
- `mizu.history`
- `mizu.archive`
- `mizu.moods`
- `mizu.memories`
- `mizu.notes`
- `mizu.weather`
- `mizu.letters`
- `mizu.playlist`
- `mizu.quickPhrases`
- `mizu.statuses`

### 目标分层

- localStorage：少量配置、当前主题、schema 版本等启动必需数据。
- IndexedDB：聊天记录、照片 Blob、手帐、信件、记忆与备份快照。
- 迁移必须采用版本化步骤；每次迁移前创建快照；失败时保留原数据并进入安全提示状态。
- 导出默认不包含 API Key；如未来提供包含密钥选项，必须二次确认并明确风险。
- 不允许直接调用 `localStorage.clear()` 或 `indexedDB.deleteDatabase()` 来“修复”数据问题。
- 不得把聊天、照片或密钥自动上传到 Base44、GitHub 或其他云服务。

## 6. API 配置与安全

### 目标能力

- 保存多套 API 配置：名称、Base URL、模型、Key、自定义请求头。
- OpenAI 兼容接口作为通用适配路径。
- 对 OpenCode Go 等订阅接口只在实测确认 endpoint、鉴权方式、模型能力、CORS 与流式行为后标记为可用，不凭服务名称推断兼容。
- 接口自检应区分：网络不可达、CORS 失败、401/403、429、模型不存在、非流式响应、服务端错误。
- 失败时保留草稿与用户输入。

### 安全边界

- API Key 不写入 URL、不写进仓库、不写进日志、不默认包含在备份中。
- 纯前端存储的 Key 仍可被同设备访问页面的人读取；设置页应明确提示。
- 模型输出按不可信文本处理，禁止直接将未经转义的模型内容写入 `innerHTML`。
- 不引入未经确认的第三方 CDN 脚本。
- 任何代理服务必须单独说明托管位置、访问控制、费用、日志与密钥存储方式。

## 7. 音乐模块专项

目标上游：`https://github.com/Anko3o/Music-Mcp-Netease`

### 接入前必须核实

1. 上游仓库当前许可证及其非商业、署名、相同方式共享要求。
2. 原版界面入口和前后端结构。
3. Cookie 登录是否由上游明确支持，具体是完整 Cookie、`MUSIC_U` 或其他字段。
4. 真实服务端路由、启动命令、监听端口、环境变量与运行时依赖。
5. 搜索、播放 URL、歌词、歌单、登录状态等功能是否可用。
6. 网易云接口风控、账号安全与地区限制风险。

在完成源码核验前，不把“Cookie 登录可用”写成已实现能力。

### 安全硬规则

- Cookie 是账号登录凭证，绝不放进 GitHub、前端 JS、localStorage、URL、Issue、日志、截图或普通备份。
- Cookie 只能保存在用户控制的私有服务端配置/密钥存储中。
- 不使用来历不明的公共网易云代理处理用户 Cookie。
- 原版 UI 优先通过独立部署和 iframe 使用；除非许可证允许且确有必要，不复制上游代码。
- 上游许可证若为 CC BY-NC-SA 4.0 或其他非商业许可证，必须逐条遵守；任何商业化前重新审查授权。

### 方案选择

| 方案 | Cookie 登录 | 费用/门槛 | 结论 |
|---|---|---|---|
| 纯 GitHub Pages | 不适合安全保存 Cookie，也不能运行 Python 服务 | 零托管费 | 只显示未连接状态/降级入口 |
| 用户自己的设备或局域网运行上游服务 | 在服务端本机保存 Cookie | 可能零托管费，但需要设备运行与网络配置 | 可作为低成本优先验证方案 |
| Base44 / 其他托管后端 | 取决于能否安全保存密钥、运行上游 Python 服务和网络兼容性 | 免费额度与运行时限制需实测 | 先做可行性测试，不承诺免费长期运行 |
| 公共第三方实例 | 不应提交个人 Cookie | 看似零成本但风险高 | 禁止用于登录态 |

## 8. 移动端、无障碍与性能

- 重点实测 Android 手机常见宽度及 WebView。
- 使用 `100dvh` 与 safe-area inset；不遮挡状态栏、摄像头挖孔和底部手势区。
- 可点击区域尽量不小于 44×44 CSS px。
- 输入框字号至少 16px，避免移动浏览器自动缩放。
- 横向分页只用 transform 处理跟手位移，避免在拖动期间触发布局重排；尊重 `prefers-reduced-motion`。
- 图片延迟解码；聊天记录较长时采用分页或虚拟列表。
- 页面离线时允许写日记、信件和草稿，并清楚标识离线状态。
- 每个页面都要有加载、空、错误、离线状态；不出现假数据和假成功。

## 9. 分阶段实施

### P0：稳定性与数据安全（先做）

1. 建立当前分支基线与回归清单。
2. 检查并记录所有现有功能，不先重写架构。
3. 检查本地存储读写、导入导出和异常恢复。
4. 为 API 设置增加清晰的状态与错误提示；验证真实请求路径。
5. 统一手机安全区域、键盘、滚动与触控体验。
6. 逐页补齐空状态、错误状态、离线状态。
7. 保护已修复的横向滑动，不在本阶段重写手势系统。

**P0 验收：** 原有聊天、相册、手帐、信件、记忆、设置可正常使用；导出后可恢复；刷新/离线/手机键盘不破坏布局；没有意外清空数据。

### P1：音乐集成（P0 后，先核验再实施）

1. 审核上游 License 与 Cookie 登录代码。
2. 记录服务端运行依赖、路由与部署要求。
3. 在不暴露 Cookie 的前提下完成独立服务本机验证。
4. 选定托管方案前先验证手机网络、跨域、休眠、HTTPS 与费用。
5. 原版 UI 成功连接后再接入水色物语入口。
6. GitHub Pages 无服务连接时显示清楚的未连接状态。

**P1 验收：** Cookie 未进入仓库和浏览器存储；手机上能真实登录、搜索、播放和查看歌词；服务断开时不会显示假播放状态。

### P2：增强体验（按用户确认逐项做）

- IndexedDB 迁移与图片容量管理。
- 多 API 配置档案和接口自检增强。
- 聊天与音乐联动卡片。
- 备份加密。
- 可选本地代理与云同步方案评估。

## 10. GitHub 执行约束

每个阶段按以下流程：

1. 只在 `feat/pure-frontend-polish` 修改。
2. 修改前检查当前文件与现有功能，不覆盖未知改动。
3. 一次聚焦一个小目标，提交信息说明具体改动。
4. 运行可用的静态检查、构建或浏览器测试；若无法执行，明确说明未验证。
5. 生成预览并检查 Android 窄屏。
6. 汇报提交链接、变更文件、测试结果、已知限制。
7. 不合并 PR，不改 main/master，不打 APK，直到用户明确提出。

## 12. 给 GitHub 开发助手的总提示词

你是水色物语项目的维护工程师。先阅读本文件和仓库现状，再按 P0 → P1 → P2 顺序实施。只允许在 `feat/pure-frontend-polish` 工作。不要修改 main/master，不要合并 PR，不要打包 APK。不要擅自重写现有首页或横向滑动系统。每次只实施一个可验证的小阶段，修改前检查现有数据结构与调用关系。任何数据迁移先做快照，任何不确定的功能先调查源码和真实接口，不得伪造完成状态。API Key 与音乐 Cookie 绝不能提交到仓库或暴露给前端。完成每一阶段后运行能运行的测试，列出实际变更、测试结果、未完成项和风险，并提供 GitHub 提交与预览链接。若需求与现有实现冲突，优先保护用户数据与现有可用功能，并先说明差异再行动。
